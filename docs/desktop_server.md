# Desktop Server Subsystem (`rust_core/desktop_server`)

The `desktop_server` crate is a local HTTP server that acts as the development and testing gateway for the Document-to-Reader ecosystem. While the production application executes its native Rust code via C++ JSI bindings directly inside iOS and Android host processes, the desktop server exposes these exact same native capabilities over a local network loopback.

This architecture enables **Zero-Emulator Browser Web-Testing**, allowing developers to build, test, and iterate on the React Native UI and Rust backend entirely within a standard desktop web browser.

---

## 1. Asynchronous Web Architecture (`axum` + `tokio`)

The server is built on top of the modern, non-blocking `axum` web framework and the `tokio` asynchronous runtime.

* **High-Concurrency:** Replaced legacy blocking HTTP implementations to support concurrent request handling. This allows the frontend to stream large document assets while simultaneously polling for inference generation status or vector math calculations.
* **Unified Error Handling:** Fully integrated with the `contracts` crate's `AppError` enums. Any panics or failures originating deep within the Rust core (like PDF parsing or LLM context failures) are caught by Axum error handlers and returned as cleanly formatted HTTP 500 JSON responses.

---

## 2. Zero-Emulator SQLite Gateway

One of the primary challenges of testing React Native applications in a web browser is the lack of native `expo-sqlite` support. The desktop server solves this by acting as a dynamic database provider.

* **The `/db` Endpoint:** The server exposes the active, populated SQLite `.db` file at `http://localhost:8080/db`.
* **WASM Integration:** When the Expo frontend detects it is running on the `web` platform, it bypasses the native JSI bridge. Instead, it boots up a `sql.js` WASM engine, fetches the database binary from the desktop server, and loads it into browser memory.
* **Visual QA:** This allows developers to run complex, data-heavy layout tests (like rendering the Shopify `FlashList` with pre-measured heights and multi-pane routing) directly in Chrome or Firefox, using real database artifacts generated by the ingestion pipeline.

---

## 3. Pipeline Execution Endpoints

The server exposes RESTful routes that map directly to the underlying `rust_core` crates, allowing developers to trigger and inspect specific pipeline phases without interacting with the mobile UI.

* **Pass 1 Extraction (`/api/parse`)**: Accepts raw document uploads (PDF, EPUB, MD) and executes the static layout analysis via the `parser` crate, returning the raw coordinates and text overlap chunks.
* **Agentic Pass 2 (`/api/delineate`)**: Triggers the ReAct LLM loop from the `agent_harness`. It pipes the raw text to the local model (via the `inference` crate) and outputs the finalized JSON `ASTNode` structures.
* **Vector Math & Embeddings (`/api/vector`)**: Provides direct access to the C++ SIMD hardware-accelerated cosine similarity logic for debugging FTS5 and hybrid RRF search weights.

---

## 4. CORS & Environment Configurations

Because the React Native Web bundler typically runs on a separate local port (e.g., `8081`) from the Rust backend (`8080`), the desktop server is configured with a permissive, CORS-compliant middleware layer.

* **Cross-Origin Resource Sharing:** Explicitly configured to allow `GET`, `POST`, and `OPTIONS` requests from standard local development origins, preventing browser preflight blocks during UI iteration.
* **Build-Time Gating:** The server leverages the global compile-time configuration variables to enable granular, extensive debug logging to the standard output terminal during pipeline execution.
